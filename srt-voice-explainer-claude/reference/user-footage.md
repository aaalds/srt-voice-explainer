# 用户实拍素材接入

用户丢过来一段录屏或实拍（"用一下 assets 下面的视频，给它缩放让大家看清楚"）时，
这一节是流程。**做错的默认做法是：把整段视频塞进一个框里，再用 CSS `scale` 放大。**
那样放大的是已经被压过一次的像素，字会糊；而且一放大就装不下，只能配合持续推移，
于是又撞上铁律 9。

## 0 · 不动用户的原始文件

原始文件只读。所有派生媒体写进 `video_work/<project>/assets/`，
并把原始文件的 sha256 记进 `manifest.json`。裁切参数写进 `design.md` 或分镜，
下次要改构图时不用重新对着视频数像素。

## 1 · 先验源

```bash
ffprobe -v error -select_streams v:0 \
  -show_entries stream=width,height,r_frame_rate,nb_frames,codec_name \
  -show_entries format=duration -of default=nw=1 "<原片>"
```

要知道的三件事：**原生分辨率**（决定你能放大到什么程度）、**有没有音轨**
（有就必须丢掉，见下）、**内容区在画面里的位置**（录屏常有大片空白边栏）。

## 2 · 音轨一律丢掉

实拍的环境音、键盘声、系统提示音会和旁白打架，而且它没经过母带，
会把逐单元响度一致性直接打穿。派生的所有视频片段都加 `-an`。
片子里只存在一条音轨：`narration.wav`。

## 3 · 放大 = 切原生像素，不是缩放视频

判据是**目标画布上的字高**。1080 宽的竖屏里，屏幕文字要看得清，字高至少 40 px；
想舒服一点就 60–80 px。反推：

```
需要的源像素高度 = 目标字高 ÷ (取景框宽度 ÷ 源裁切宽度)
```

一段 4K 录屏里 30 px 高的字，裁一块 1760 px 宽的区域放进 880 px 宽的取景框，
缩放系数 0.5 → 落到画布上只有 15 px，不可读。同一块区域按 1.0 显示则是 30 px，
但一屏只能装下一半宽度——**这正是要分步推近的原因，不是缺陷**。

所以分两类素材：

| 用途 | 形式 | 命令 |
| ---- | ---- | ---- |
| 建立"这是真的" | 视频片段，看得到进度在走、光标在动 | `crop` + `scale` 到取景框宽度，`-an` |
| 逐处标注细节 | **原生像素静帧**，一处一张 | `crop=W:H:X:Y`，不 `scale` |

```bash
# 全景片段：从 4K 里切出内容区，缩到取景框宽度，丢音轨
ffmpeg -i "<原片>" -vf "crop=2872:2160:250:0,scale=1080:812" -an -c:v libx264 -crf 18 assets/shot-full.mp4

# 细节静帧：原生像素，一个字都不缩
ffmpeg -i "<原片>" -vf "crop=1760:272:1070:44" -frames:v 1 assets/prompt.png
```

静帧的坐标从原片的**某一固定帧**上量（`-ss` 定位后 `-frames:v 1` 导出全帧再量），
不要凭记忆估。量错 20 px，下划线就会歪在字的下一行上。

## 4 · 取景参数化，别手调 transform

给每个素材层一个 `transform-origin: 0% 0%` 的变换容器，
然后只写"我要把源图上的哪个点、以多大倍率、送到取景框正中"：

```js
const VW = 880, VH = 480;                       // 取景框尺寸
const view = (s, tx, ty) => ({ scale: s, x: VW / 2 - tx * s, y: VH / 2 - ty * s });

setView("#v-prompt", view(0.5, 880, 136), 0);            // 初始：整块气泡缩着看
toView("#v-prompt", view(1.0, 512, 82), at("b012", 0.16), 0.55);   // 推近到首句
toView("#v-prompt", view(1.0, 1408, 88), at("b013", 0.05), 0.60);  // 横移到模型段
```

这样调构图只改三个数（倍率 + 源坐标），不用手算 `translate`。
每一次取景变化都对齐到某个节拍的发音时间，不要自己定节奏。

## 5 · 移到位就停住

`toView` 的时长控制在 0.4–0.6 s，**到位之后这个节拍剩下的时间完全静止**。

- 持续缓慢推移（Ken Burns）在这条管线里是禁止的：它让整幅画面每帧都在变，
  静态稳定性门禁会判全局漂移，观众也会觉得画面在"飘"。
- 静帧层放大后是完全静止的，所以取景框里的"动"必须由**取景变化本身**
  或**标注元素**（下划线、方框、标签）承担，而且要落在节拍上。

标注用 `scaleX` 从 0 长出来的下划线最稳：它有明确的运动动词（"点亮"），
面积小，不会触发漂移判据。

## 6 · 取景框宽度先过安全区

媒体面板天生要宽，是最容易撞平台覆盖区的元素。竖屏右侧 140 px 是点赞栏，
一个 960 px 宽、左边距 60 px 的面板右边缘在 1020 px——已经进去了。
**先按安全区定取景框宽度，再算取景参数**，反过来会返工：

```
可用宽度 = 1080 − 左边距 − 右侧 140
```

装饰性边框可以压线，正在被标注的内容不行。定完跑
`safe_area_check.py` 确认，不要靠眼睛判断。

## 7 · HyperFrames 里的 `<video>`

细节见 `hyperframes-traps.md` 的「实拍素材」一节。要点：

- `<video>` 是**未计时父层的直接子元素**，自己带 `data-start` / `data-duration`，
  需要从素材中段开始就加 `data-media-start`。
- `muted playsinline`，显式写 `width` / `height`，不要给 `class="clip"` 或 `opacity: 0`——
  可见性由框架接管，自己压 `opacity` 会让它永远不出画。
- 同一个 `src` 用在两处会报 `duplicate_media_discovery_risk`，官方标注为 benign，
  但必须抽帧确认两段都出画了才能接受。
- `check` 的快照工具**不解码视频**，媒体位置在快照里是黑的；这不是缺陷，
  用一次草稿渲染抽帧确认，别去"修"一个不存在的问题。

## 8 · 内容要对得上

实拍是证据，不是壁纸。旁白说"在 agents 目录下建文件"时，画面上被标注的
必须就是那个路径；说"reasoning effort 设 max"时，标注的必须是那一行。
标注位置和旁白对不上，比不用实拍更糟——观众会发现你在糊弄。

如果原片里某个字段根本不存在，不要为了凑画面去标注一个相近的东西，
改旁白或改标注对象，并把这件事记进 `SCRIPT_CHANGES.md` / 分镜。
